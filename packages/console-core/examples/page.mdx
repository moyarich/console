# @moyarich/console-core

Portable addon, extension-point, capability, service, and lifecycle contracts shared by Console hosts and addons.

The package remains independent of the React host implementation.

## When to use Core

Use Core when you are creating an addon or a headless host. To display a console in React or configure a ready-made addon, start with [@moyarich/console](#/package-console/overview); its component owns the manager lifecycle.

Core defines how addons activate, register behavior, share services, and clean up. It does not render React UI. The runnable examples below create a manager explicitly to show what a host does.

Portable or headless addons can depend only on core:

```ts
import {
  consoleExtensionPoints,
  consoleServices,
  type ConsoleAddon,
} from "@moyarich/console-core";
```

`@moyarich/console` is the React host implementation and re-exports core contracts for application convenience.

Core is a capability boundary, not a restriction on addon design. Addons that only need shared contracts should prefer `@moyarich/console-core`; addons that intentionally use React-host-specific APIs may also depend on `@moyarich/console`.

## Callback convention

Extension contributions use one immutable context object. The primary value is part of that context instead of being passed as a separate positional argument.

```ts
host.extensions.register(
  consoleExtensionPoints.messageFilter,
  ({ message }) => {
    return message.method !== "debug";
  },
);

host.extensions.register(consoleExtensionPoints.processOutputProcessor, {
  id: "strip-prefix",
  process({ output, text, stream }) {
    if (stream !== "stdout" || !text.startsWith("[worker] ")) {
      return undefined;
    }

    return {
      data: output.data.replace("[worker] ", ""),
    };
  },
});
```

This keeps callback signatures stable as the SDK grows: new host information can be added to the context without adding positional parameters. Context values are readonly inputs; processors and parsers return result/patch objects instead of mutating host-owned state.

## Composition and ordering

Each extension token exposes its composition model:

```ts
consoleExtensionPoints.processOutputProcessor.composition; // "pipeline"
consoleExtensionPoints.messageRenderer.composition; // "first-result"
consoleExtensionPoints.panelElement.composition; // "collect"
consoleExtensionPoints.messageFilter.composition; // "all"
consoleExtensionPoints.frameDecorator.composition; // "middleware"
```

Contributions are resolved by descending `priority`, then stable registration order for equal priorities. Normal addon order should be preferred; `priority` is an explicit override for cases such as placing a specialized parser before a generic parser.

For pipeline points, each contribution sees the immutable result from previous contributions:

```text
input
  ↓
processor A
  ↓ A result
processor B
  ↓ B result
processor C
  ↓
final output
```

This means transform order can change the result, just as it can in Vite, unified/rehype, or compiler plugin pipelines.

## Extension-point selection

Addons should use the narrowest generic `consoleExtensionPoints.*` contract that matches the behavior they contribute:

| Extension point          | Composition    | Purpose                                                        |
| ------------------------ | -------------- | -------------------------------------------------------------- |
| `processControlParser`   | `pipeline`     | Parse stateful raw process controls before line normalization. |
| `processOutputProcessor` | `pipeline`     | Transform or enrich logical ANSI/process output.               |
| `structuredOutputParser` | `first-result` | Promote terminal text into structured values.                  |
| `linkProvider`           | `collect`      | Detect application-specific links and actions.                 |
| `outputRenderer`         | `first-result` | Replace the complete output surface.                           |
| `frameDecorator`         | `middleware`   | Structurally wrap the complete Console frame.                  |
| `emptyStateRenderer`     | `first-result` | Customize only an empty output surface.                        |
| `panelElement`           | `collect`      | Add persistent UI at generic panel placements.                 |
| `messageFilter`          | `all`          | Contribute structured-message visibility rules.                |
| `messageRenderer`        | `first-result` | Replace a complete structured message row.                     |
| `messageDecoration`      | `collect`      | Add UI around a row without replacing it.                      |
| `messageTextProvider`    | `collect`      | Add logical searchable/plain text for a message.               |
| `valueRenderer`          | `first-result` | Customize an individual structured value.                      |
| `keyboardShortcut`       | `first-result` | Add keyboard commands scoped to the focused Console.           |
| `panelAction`            | `collect`      | Add Console-level actions.                                     |
| `contextMenuAction`      | `collect`      | Add context-menu actions.                                      |
| `messageAction`          | `collect`      | Add actions scoped to one structured message.                  |

`frameDecorator` is intentionally structural. Persistent feature UI such as search, filtering, status, retention, or progress controls should normally use `panelElement` so independent addons compose without becoming nested frame wrappers.

## Lifecycle and cleanup

Each addon has a stable `id` and an `activate(host)` method. Keep stateful React addons stable with `useMemo`. The host creates a disposable scope for each activation and removes scoped extension/service registrations when the addon unloads.

Register external resources with `host.scope.defer(cleanup)`. Returning a cleanup function from `activate` also registers it with the scope. Disposal is idempotent; disposing a manager unloads its addons in reverse activation order.

[Run the cleanup example](#/package-console-core/addon-sdk/addon-cleanup) to register an event listener with an `AbortController` signal. Unloading the addon aborts the signal and removes the listener; sending more events leaves the counter unchanged.

## Shared services

A service token identifies one typed provider. Providers register through `host.services.provide`; consumers use `host.services.require`. Load the provider before its consumers. Duplicate providers are rejected.

[Run the shared service example](#/package-console-core/addon-sdk/shared-addon-services).

## Custom extension points

Use `createConsoleExtensionPoint` to declare a typed contribution contract. The owning host or addon must consume the registered contributions; registering a custom token alone does not add UI or behavior.

[Run the custom extension point example](#/package-console-core/addon-sdk/custom-extension-points).
