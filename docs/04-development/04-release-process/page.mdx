# Release process

Each publishable package in the npm workspaces has its own version, changelog, and release identity. Preparing and approving a release is separate from publishing its npm package.

## Release lifecycle

```text
Prepare release PR (release/prepare-*)
    ↓ review changes and required CI
Merge approved PR into main
    ↓ release-approved-pr.yml runs
Verify approved release preparation and package matrix
    ↓ create or update GitHub Release drafts
Review drafts
    ↓ separately start a publishing workflow when ready
Publish npm packages (manual, explicit action)
```

**Merging a release-preparation PR only prepares GitHub Release drafts. It does not publish npm packages or automatically finalize GitHub Releases.**

## Prepare a release PR

Use the repository's release-preparation workflow to select publishable packages and prepare their versions, changelogs, and related package changes in a `release/prepare-*` pull request targeting `main`.

Review the selected package list, dependency changes, changelog entries, and CI status before merging. Packages not approved in the preparation PR are not implicitly added to the release.

## After the approved PR is merged

`.github/workflows/release-approved-pr.yml` runs on closed pull requests targeting `main` when **all** of the following are true:

- The PR was **merged**, not merely closed.
- The PR branch belongs to this repository.
- The source branch name starts with `release/prepare-`.

It invokes `moyarich/reusable-workflows/.github/workflows/reusable_approved-release.yml@main` with `dry-run: false`.

The shared workflow then:

1. **Verifies** that the merged PR qualifies as an approved release preparation and satisfies the configured required-workflow checks.
2. **Plans** and validates the approved package names, workspace directories, and versions. A missing or invalid package matrix stops the process.
3. **Drafts** a GitHub Release for each approved package using its package-specific version, tag, and changelog.

Draft jobs run with `fail-fast: false` and `max-parallel: 1`; errors in one draft do not automatically cancel the other draft jobs, but the overall workflow reports failures.

The draft process **does not publish to npm**. The npm publishing workflow is separate and must be explicitly run.

## Review and publish packages separately

Review the package-specific GitHub Release drafts and their changelog-based notes before publishing.

When ready, use **Publish npm package** (`.github/workflows/publish.yml`) via GitHub Actions **Run workflow**. Select the package or `all`, the registry, and other inputs. Its `dry-run` input defaults to `true`; explicitly disable dry run only when a real publish is intended. That workflow uses `reusable_bulk-npm-publish.yml@main`.

The independent **Release package** workflow (`.github/workflows/release.yml`) is also manually dispatched and defaults to `draft: true` and `dry-run: true`. It is not part of the post-merge approved-release workflow.

## Package identity and release notes

Use each package's `package.json` version and package-specific `CHANGELOG.md` as the source of its published version and public release notes. GitHub Release drafts are not a substitute for publishing an npm package.

Public release notes should describe user-visible API changes, addon features, rendering behavior, fixes, and compatibility. Keep internal CI changes, repository moves, and build tooling details in pull requests and development documentation.
